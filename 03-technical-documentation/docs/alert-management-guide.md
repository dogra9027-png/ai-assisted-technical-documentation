# Nexus IT Operations Platform
## Alert Management User Guide

**Document Version:** 1.0  
**Audience:** IT Operations Analysts, Administrators, and authorized users  
**Document Status:** Portfolio Demonstration  
**Product:** Fictional Nexus IT Operations Platform

---

## 1. Overview

The alert management functionality helps IT operations teams review and monitor alerts generated by infrastructure conditions.

Users can review alert descriptions, assess severity, filter alerts, and track alert status. Users with the appropriate permissions can also acknowledge alerts to indicate that they have been reviewed.

This guide explains the alert concepts, available actions, and role-based permissions defined in the product specifications.

## 2. Before You Begin

Before working with alerts, understand the following:

- Your assigned user role determines which alert actions you can perform.
- All three defined roles can view alerts.
- Only Administrators and Operations Analysts can acknowledge alerts.
- Alert severity and alert status describe different aspects of an alert.

## 3. Understanding Alert Severity

Severity indicates the urgency or operational significance of an alert.

Nexus defines four severity levels:

| Severity | Meaning | Recommended attention |
|---|---|---|
| Critical | Requires immediate investigation. | Prioritize immediate investigation. |
| High | Indicates a significant operational concern. | Investigate promptly. |
| Medium | Requires investigation and monitoring. | Review and monitor the condition. |
| Low | Informational or lower-priority condition. | Review according to operational priorities. |

Use severity to help prioritize which alerts require attention first.

## 4. Understanding Alert Status

Status indicates the current state of an alert.

| Status | Definition |
|---|---|
| Active | The alert has been generated and requires review. |
| Acknowledged | An authorized user has reviewed the alert. |
| Resolved | The underlying condition has been addressed. |

**Important:** Acknowledging an alert does not mean that the underlying condition has been resolved. Review and resolution are separate concepts.

## 5. Reviewing Alerts

Authorized users can access the alert list and review the information associated with generated alerts.

The defined alert information includes:

- Alert description.
- Severity.
- Status.

When reviewing an alert:

1. Read the alert description to understand the reported condition.
2. Check its severity to assess urgency.
3. Check its status to understand whether it requires review, has been acknowledged, or has been resolved.
4. Determine whether further investigation is required according to your organization's operational procedures.

The available product specifications do not define the exact screen names, navigation labels, or alert-detail layout. This guide therefore describes the supported workflow without assuming unverified interface controls.

## 6. Filtering Alerts

The detailed functional specifications define filtering by:

- Severity.
- Status.

Filtering helps users narrow the alert information they need to review.

The exact filter controls and interface labels have not been specified.

**Specification clarification:** The Product Overview refers to filtering by status and category, while functional requirement ALT-003 specifies severity and status. This guide follows ALT-003 pending confirmation from the product team. Category filtering should not be documented as an available function until the discrepancy is resolved.

## 7. Acknowledging Alerts

Acknowledgement indicates that an authorized user has reviewed an alert.

The following roles can acknowledge alerts:

- Administrator.
- Operations Analyst.

The Viewer role can review alerts but cannot acknowledge them.

Before acknowledging an alert, review its description, severity, and status.

**Note:** The specifications define the acknowledgement capability but do not describe the exact user-interface steps or confirmation behaviour. Consult the approved product interface documentation when those details become available.

## 8. Role-Based Permissions

Alert access is controlled by the user's assigned role.

| Role | View alerts | Acknowledge alerts |
|---|---|---|
| Administrator | Yes | Yes |
| Operations Analyst | Yes | Yes |
| Viewer | Yes | No |

If the acknowledgement action is unavailable to a user, check the permissions associated with their assigned role or contact the appropriate administrator.

## 9. Monitoring Alert Status

Use alert status to understand the progress of an alert:

- **Active:** Requires review.
- **Acknowledged:** Reviewed by an authorized user.
- **Resolved:** The underlying condition has been addressed.

Do not treat acknowledgement as confirmation that an infrastructure issue has been fixed.

The specifications do not define how alerts are resolved or whether users can manually change an alert to Resolved. Those procedures require product-team confirmation before they can be documented.
