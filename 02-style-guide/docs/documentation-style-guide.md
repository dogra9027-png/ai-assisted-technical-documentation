# Nexus IT Operations Platform
## Documentation Style Guide

**Document Type:** Documentation Standards  
**Version:** 1.0  
**Status:** Portfolio Demonstration

---

## 1. Purpose

This style guide establishes writing, formatting, terminology, and content standards for all Nexus IT Operations Platform documentation.

Its purpose is to ensure that documentation is clear, consistent, accurate, accessible, and easy to maintain.

These standards apply to user guides, administrator documentation, technical instructions, troubleshooting articles, release notes, and training materials.

## 2. Audience and Writing Approach

Documentation must be written according to the intended audience.

| Audience | Writing Approach |
|---|---|
| End users | Clear, task-oriented instructions with minimal technical jargon |
| Administrators | Detailed procedures covering configuration, permissions, and operational tasks |
| Developers | Precise technical explanations, API terminology, and structured examples |
| IT managers | Concise explanations emphasizing operational impact and reporting |

Use direct language and explain technical terms when they are first introduced.

## 3. Voice and Tone

All documentation must use a professional, neutral, and helpful tone.

### Writing principles

- Use active voice wherever possible.
- Address the reader as "you" when giving instructions.
- Use present tense for describing product behaviour.
- Keep sentences concise and focused.
- Avoid unnecessary technical jargon.
- Avoid vague statements and unsupported claims.
- Use consistent terminology throughout the documentation.

**Preferred:**

"Select Acknowledge to mark the alert as reviewed."

**Avoid:**

"The alert should be acknowledged by the user by selecting the appropriate option."

## 4. Headings and Structure

Use descriptive headings that clearly communicate the content of each section.

Follow this hierarchy:

- H1: Document title
- H2: Main sections
- H3: Subsections
- H4: Supporting details, when necessary

Use sentence case for headings.

**Preferred:** Configure user access

**Avoid:** Configure User Access

Organize procedures in the order that users perform them.

## 5. Instructional Writing

Write procedures as numbered steps.

Each step should describe one primary action.

Use imperative verbs to begin instructions.

**Example:**

### Acknowledge an alert

1. Sign in to the Nexus platform.
2. Open the Alert Management page.
3. Select the alert you want to review.
4. Select **Acknowledge**.
5. Confirm that the alert status changes to Acknowledged.

Use notes and warnings only when they provide information necessary to complete a task safely or correctly.

## 6. Formatting Standards

| Element | Standard |
|---|---|
| Bold | Interface labels, buttons, and important terms |
| Italic | Titles and occasional emphasis |
| Code formatting | Commands, filenames, paths, and technical values |
| Tables | Comparisons, permissions, and structured reference information |
| Numbered lists | Sequential procedures |
| Bullet lists | Non-sequential information |

Use Markdown consistently.

## 7. Terminology Standards

Use the approved terminology defined in the terminology glossary.

Examples:

| Preferred Term | Avoid |
|---|---|
| Alert | Notification, warning (when referring to an alert record) |
| Acknowledged | Accepted, confirmed (when referring to alert status) |
| Incident | Problem, ticket (when referring to an incident record) |
| Administrator | Admin (in formal documentation) |
| Viewer | Read-only user (when referring to the defined role) |
| Sign in | Login (when used as a verb) |

Preserve the exact names of product features, roles, and status values.

## 8. Screenshots and Visuals

When screenshots are included:

- Use clear and readable images.
- Capture only the relevant interface area.
- Remove unrelated personal or sensitive information.
- Add descriptive captions.
- Refer to visuals by their assigned figure number.
- Ensure that screenshots match the accompanying instructions.

Do not use fabricated screenshots as evidence of a functioning product.

## 9. Tables and Reference Information

Use tables when information is easier to understand in a structured format.

Tables should:

- Have descriptive column headings.
- Use consistent terminology.
- Avoid excessive text.
- Include all information necessary to interpret the values.

## 10. Accessibility and Readability

Documentation should be accessible to readers with different levels of technical knowledge.

- Use descriptive link text.
- Provide meaningful alternative text for images.
- Avoid relying on colour alone to communicate status.
- Use short paragraphs.
- Explain abbreviations when first introduced.
- Use clear and descriptive section headings.

## 11. Quality Assurance

Before publication, review every document for:

- Technical accuracy against approved product specifications
- Correct terminology
- Clear and complete instructions
- Consistent formatting and heading structure
- Grammar, spelling, and punctuation
- Working internal and external links
- Appropriate screenshots and captions
- Accessibility and readability

## 12. AI-Assisted Content Standards

AI tools may support drafting, summarization, restructuring, and editorial review.

However:

- AI-generated content must be treated as draft material.
- Product behaviour must be checked against approved specifications.
- Unsupported technical details must not be presented as facts.
- Commands, configuration examples, and procedures require validation.
- Human review is required before publication.
- Confidential information must not be entered into unauthorized AI tools.

The documentation owner remains responsible for the accuracy and quality of published content.
